2. Q1 — render-function-page vs. App Router

why

Keep the switch for top-level fn. Your FunctionsNav resolves the enabled function list per location at request time via useLocationFunctionsQuery — the set of valid fn values isn't static across locations, it's config-driven. A folder-per-fn approach doesn't remove that dynamism (Next still needs code for every possible fn folder regardless), and a switch is the clearer place to encode "if this fn isn't recognized, notFound()".

Don't extend the switch for anything nested inside a feature. Add-amenity and view-amenity are permanently-fixed children of "provide-amenities" — they don't vary by location or config. That's exactly what folder-based routing is for: browser back/forward, deep-linking, per-route loading/error boundaries, and no more string-concatenated fn values to keep in sync in three places.

Rule of thumb: dynamic sibling set → switch. Fixed nested children → folders.

3. Q2 — Breadcrumbs at every nesting level

Your breadcrumb is really two independent trails glued together:

  • Location trail (Museum of the Bible › Grand Hall › theater) — already solved by getNodeAndPathBySlug(tree, slug). This works at any depth today; nothing changes here.
  • Feature trail (Provide Amenities › Add Amenity) — this is what's currently missing a home. It should be built once, in the [fn]/layout.tsx, from the route segments below fn.
why

Centralizing this in a layout (rather than each page hardcoding its own crumb array) means every future nested page under any fn gets breadcrumbs for free just by existing in the folder tree — you're not maintaining a parallel breadcrumb map. Use useSelectedLayoutSegments() (client) or read the matched route in the server layout to know how deep you are, and a small label lookup ({ 'add-amenity': 'Add Amenity', 'view-amenity': 'View Amenity' }) for display text.

Answer: yes, breadcrumbs work identically regardless of location nesting depth or feature nesting depth, as long as both trails are composed from actual route/tree data rather than hand-typed per page.

4. Q3 — Folder structure for create/view

location/[slug]/[fn]/ ├── page.tsx (existing — dispatch via render-function-page) ├── render-function-page.tsx (existing — reverted, top-level fn switch only) ├── layout.tsx NEW — breadcrumb shell for this fn + children ├── add-amenity/ │ └── page.tsx NEW — create flow └── view-amenity/ └── [amenityId]/ └── page.tsx NEW — view/edit flow, keyed by amenity id
note

[fn] is a single dynamic segment, so add-amenity and view-amenity folders nested under it will technically match under any fn value (e.g. /location/x/plan-selection/add-amenity would also resolve to this file). Guard against that explicitly in each page by checking fn === 'provide-amenities' and calling notFound() otherwise — shown in the code below. This is a one-line safeguard, not a reason to avoid the nested-folder approach.

why

view-amenity needs an amenityId segment, not just the location context — you're viewing/editing one specific amenity, so it must be addressable and shareable as its own URL (.../view-amenity/amn_123), and it lets you fetch that single amenity server-side before render instead of passing it through client state.

add-amenity doesn't need an id — it's a fixed creation form scoped to the location, so no extra dynamic segment required.

[fn]/layout.tsx — breadcrumb shell

src/app/(protected)/location/[slug]/[fn]/layout.tsx 
import { getLocationsTree } from '@/modules/locations/actions/server-locations';
import { getNodeAndPathBySlug } from '@/modules/locations/lib/utils';
import { Breadcrumbs } from '@/components/layout/Breadcrumbs';
import { buildFeatureCrumbs, FN_LABELS } from '@/lib/breadcrumbs';

interface Props {
  children: React.ReactNode;
  params: Promise<{ slug: string; fn: string }>;
}

export default async function FnLayout({ children, params }: Props) {
  const { slug, fn } = await params;

  const tree = await getLocationsTree();
  const found = getNodeAndPathBySlug(tree, slug);

  const locationCrumbs =
    found?.path.map((node) => ({
      label: node.name,
      href: `/location/${node.slug}`,
    })) ?? [];

  const featureCrumbs = buildFeatureCrumbs(slug, fn);

  return (
    <div>
      <Breadcrumbs items={[...locationCrumbs, ...featureCrumbs]} />
      {children}
    </div>
  );
}

lib/breadcrumbs.ts — shared crumb builder

src/lib/breadcrumbs.ts 
export const FN_LABELS: Record<string, string> = {
  'provide-amenities': 'Provide Amenities',
  'plan-selection': 'Plan Selection',
  configurations: 'Configurations',
  tickets: 'Tickets',
};

const LEAF_LABELS: Record<string, string> = {
  'add-amenity': 'Add Amenity',
  'view-amenity': 'View Amenity',
};

/**
 * Builds the "feature" portion of the breadcrumb trail from the fn slug
 * and (optionally) a trailing leaf segment, e.g. add-amenity / view-amenity.
 * Location portion is built separately from the locations tree.
 */
export function buildFeatureCrumbs(
  locationSlug: string,
  fn: string,
  leaf?: string,
) {
  const crumbs = [
    {
      label: FN_LABELS[fn] ?? fn,
      href: `/location/${locationSlug}/${fn}`,
    },
  ];

  if (leaf) {
    crumbs.push({
      label: LEAF_LABELS[leaf] ?? leaf,
      href: `/location/${locationSlug}/${fn}/${leaf}`,
    });
  }

  return crumbs;
}

add-amenity/page.tsx — create flow

src/app/(protected)/location/[slug]/[fn]/add-amenity/page.tsx 
import { notFound } from 'next/navigation';
import { getLocationsTree } from '@/modules/locations/actions/server-locations';
import { getNodeAndPathBySlug } from '@/modules/locations/lib/utils';
import { AddAmenityForm } from '@/modules/amenities/components/forms/AddAmenityForm';

interface Props {
  params: Promise<{ slug: string; fn: string }>;
}

export default async function AddAmenityPage({ params }: Props) {
  const { slug, fn } = await params;

  // Guard: this nested route only makes sense under provide-amenities,
  // since [fn] is a single dynamic segment shared by all features.
  if (fn !== 'provide-amenities') notFound();

  const tree = await getLocationsTree();
  const found = getNodeAndPathBySlug(tree, slug);
  if (!found) notFound();

  const locationId = Number(found.node.id);

  return <AddAmenityForm locationId={locationId} locationSlug={slug} />;
}

view-amenity/[amenityId]/page.tsx — view/edit flow

src/app/(protected)/location/[slug]/[fn]/view-amenity/[amenityId]/page.tsx 
import { notFound } from 'next/navigation';
import { getLocationsTree } from '@/modules/locations/actions/server-locations';
import { getNodeAndPathBySlug } from '@/modules/locations/lib/utils';
import { getAmenityById } from '@/modules/amenities/actions/server-amenities';
import { ViewAmenityDetail } from '@/modules/amenities/components/ViewAmenityDetail';

interface Props {
  params: Promise<{ slug: string; fn: string; amenityId: string }>;
}

export default async function ViewAmenityPage({ params }: Props) {
  const { slug, fn, amenityId } = await params;

  if (fn !== 'provide-amenities') notFound();

  const tree = await getLocationsTree();
  const found = getNodeAndPathBySlug(tree, slug);
  if (!found) notFound();

  const amenity = await getAmenityById(amenityId);
  if (!amenity) notFound();

  return (
    <ViewAmenityDetail
      amenity={amenity}
      locationId={Number(found.node.id)}
      locationSlug={slug}
    />
  );
}
